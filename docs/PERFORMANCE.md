## 二、 核心性能瓶颈分析与已落地解决方案

### 2.1 规则集冷启动限流风暴与单点故障治理

#### 【问题根因】
- 本项目声明了 94 个独立的 HTTP `rule-provider`。
- **冷启动鸡生蛋死锁 (Bootstrap Deadlock)**：若规则集指定 `proxy: 节点选择`，在客户端首次冷启动加载配置阶段，由于代理通道尚未完成健康检查建连，内核在初始化规则阶段强行通过未就绪代理拉取，会导致连接瞬间被切断报 `EOF`。
- **TLS 重协商断流**：若采用 `testingcf.jsdelivr.net` 等 Cloudflare 测试镜像，其主动触发的 TLS 重协商请求会被 Go 语言标准库直接切断（报 `EOF`）。

#### 【已落地优化方案】
- **国内直连高可用 CDN 架构**：全量规则集与图标资源默认迁移至 `fastly.jsdelivr.net`，实测大陆直连 0.5s HTTP 200，无 TLS 重协商阻断。
- **默认通道解耦为 DIRECT**：彻底斩断冷启动时对代理节点的握手依赖死锁，规则集在客户端启动瞬间毫秒级静默拉取完毕。
- **CONFIG 运行时声明式切换**：在 JS 顶部提供 `ruleProviderProxy`（`"DIRECT"` / `"节点选择"`）与 `ruleProviderCdn` 开关，按需在客户端直接微调。
- **24 小时懒加载更新周期**：所有 provider 配置 `interval: 86400`，杜绝短时间内的无谓重复拉取。

### 2.2 策略组健康检查测速风暴 (Health Check Storm) 治理

#### 【问题根因】
- 过去 `自动选择` 策略组配置为 `lazy: false` 且未设容差，无论是否有流量走该组，每隔几分钟对节点池内数百个节点并发发起测速。
- 在节点延迟波动（如 50ms 与 52ms 之间）时，由于没有容差阈值，策略组发生频繁乒乓震荡，导致长连接应用频繁断流。

#### 【已落地优化方案】
在 `config/rules_profile.json` 与生成器中，将自动选择与地区策略组全部调优为：
```yaml
- name: "自动选择"
  type: url-test
  interval: 600      # 探测间隔延长至 10 分钟 (降低 50% 探测并发)
  tolerance: 50      # 设定 50ms 容差阈值 (彻底消灭乒乓频繁切换)
  lazy: true         # 懒测速模式：无流量经过时不主动测速
```

### 2.3 节点池膨胀与内存/连接表开销治理

#### 【问题根因】
- 大部分商业机场订阅中充斥着大量的无用节点（如“剩余流量：100G”、“官网防失联”、“套餐到期：2026-12-31”等）。
- 部分节点倍率高达 2x、3x、5x 甚至 10x，用户在“自动选择”或轮询时极易被高倍率节点消耗巨额流量。
- 此外，大量无效节点会显著增加客户端 UI 渲染卡顿度及内核定期探测的连接数。

#### 【已落地优化方案】
在 `customSubBoost.js` 内部集成了纯标准 ECMAScript 的高效流式节点清洗引擎：
1. **垃圾特征正则过滤**：
   - 过滤包含 `剩余流量|套餐到期|官网|更新|客服|通知` 等关键词的非代理节点。
2. **高倍率智能剔除与专线保护**：
   - 智能识别节点名称中的倍率标识（如 `2x`, `3.0x`, `| 5x` 等），凡超过 `maxMultiplier`（默认 1.5x）一律清洗。
   - 严密保护合法的专线名称（例如 `IEPL-X2` 专线属于专线代号而非 2 倍率，不会被误杀）。
3. **级联断链清洗**：
   - 节点清洗后，自动遍历并清洗所有策略组中的 `proxies` 引用列表，杜绝内核加载时出现 `proxy not found` 致命异常。
- **实测效果**：TAGMeta 订阅原始 226 个节点清洗后保留 82 个优质节点，内存占用与并发测速连接数减少超过 60%！

### 2.4 DNS 解析链路与 Fake-IP 性能调优

#### 【已落地优化方案】
1. **Fake-IP 模式全面优化**：
   - 启用 `enhanced-mode: fake-ip` 与 `fake-ip-range: 198.18.0.1/16`。
   - 客户端在发起 TCP 握手前无需等待真实的远程 DNS 递归解析返回，内核直接秒级返回 Fake-IP，将首包建立延迟 (TTFB) 缩减 80% 以上。
2. **企业工作内网独立 Nameserver Policy**：
   - 对企业内网专有域名配置独立的 DNS 服务器（如通过 `nameserver-policy` 指向企业内部专有 DNS 解析器）。
   - 避免将企业内网域名泄漏到公共公共 DoH 服务器，同时避免 Fake-IP 污染企业内部服务。
3. **Steam 握手直连优化**：
   - `cm.steampowered.com` 与 `steamserver.net` 走国内 DNS 解析与国内服务直连，确保 Steam 获取国内 IP 并快速建立会话。

### 2.5 客户端热重载延迟与策略组正则去冗余治理

#### 【问题根因】
- 在 Clash Party 等桌面客户端中启用或关闭覆写时，客户端调用内核 `PUT /configs?force=true` 接口触发全量热重载。
- 过去预编译策略组中挂载了长达 300 字符的 `exclude-filter` 垃圾特征正则。Mihomo 内核在构建 23~41 个策略组（包含 9 个 `include-all: true` 全量组）时，对数百个节点重复执行昂贵的正则编译与遍历匹配，导致内核长时间持有全局配置锁，外部 IPC API 频繁超时（报 503/504 错误），使客户端界面产生 5~10 秒白屏卡顿。

#### 【已落地优化方案】
- **双轨解耦机制 (Dual-track Decoupling)**：
  - **JS 覆写产物**：因 JS 运行时的流式节点清洗引擎已在第 1 步于内存中物理剔除了垃圾节点，预编译 JS 策略组彻底剥离多余的 `exclude-filter` 垃圾正则，为 Go 内核装配显著减负；并增加非空校验，若剥离后为空则物理删除排除键，杜绝 `regexp.Compile("")` 误杀全量节点的空正则隐患。
  - **双轨纯 YAML 产物**：完整保留原始 `exclude-filter` 正则防御，确保不支持 JS 脚本的传统客户端仍能享受无死角的垃圾节点清洗能力，坚守向后兼容底线。

### 2.6 测速协议工业级可靠性演进与教条纠偏 (HTTPS 204 vs 明文 HTTP)

#### 【历史教条与现实冲突】
- **历史盲目假设**：曾认为在代理加密隧道内，明文 `http://www.gstatic.com/generate_204` 可以节省 1 个 TLS 握手 RTT 和证书协商开销。
- **现实网络冲突**：
  1. 绝大多数商业机场与中继反代（Nginx/HAProxy/Envoy）在响应明文 HTTP 80 204 报文后，会主动发送 FIN/RST 掐断长连接，导致 Mihomo 底层 HTTP 连接池复用时频繁抛出 `use of closed network connection`；
  2. Mihomo 内核官方强烈建议使用 HTTPS 规避潜在的运营商或中继劫持（单日产生 160+ 条内核告警）；
  3. 当短时间内连续发起批量测延迟时，大量被掐断的 HTTP 80 短连接导致测速并发排队阻塞，直接引发大面积测速超时与断连假死。

#### 【已落地标准方案】
- **确立全局标准 `https://www.gstatic.com/generate_204`**：
  - 测速地址统一回归为高可靠 HTTPS 204，彻底消除中继 RST 掐断与内核劫持告警；
  - 配合 `interval: 600`（10 分钟）与 `lazy: true`（懒测速），在完全消除握手风暴的同时，确保每次探测均代表真实可复用的端到端长连接状态。

### 2.7 代理解析多路高可用与 Windows IPv6 幽灵重试根治

#### 【问题根因】
1. **中转域名大报文丢包**：商业机场单域名（如 `sankuaei.com`）常挂载多达 39 个 A 记录，单一 UDP DNS 解析器在处理超大 DNS 响应报文时偶发截断丢包；而此前过度依赖单一 DoH 又会引入 TLS 靴带解析死锁；
2. **Windows 系统直连瞬断**：`direct-nameserver: ["system"]` 单独依赖 Windows WinSock 解析器，当网络微抖动时直接导致拉取规则集与直连流量挂死；
3. **IPv6 幽灵重试延时**：Windows 环境在缺少有效 IPv6 路由时，Go `net.Dial` 仍优先尝试 IPv6 连接，持续在底层抛出 `connectex 10051 (unreachable network)`，白白引入数秒握手悬空挂起。

#### 【已落地优化方案】
1. **代理解析与主 DNS 链路双 UDP 优先 + 单 IP DoH 兜底**：
   - 主 `nameserver` 与 `proxy-server-nameserver` 统一配置为：`["223.5.5.5", "119.29.29.29", "https://223.5.5.5/dns-query"]`；
   - 阿里与腾讯双国内直连高效 UDP 在 2~5ms 内竞速秒解，超大报文或网络劣化时由纯 IP DoH 兜底（消除 doh.pub 等域名式 DoH 在 bootstrap 时引发的 A/AAAA 预解析死循环），彻底消除 TCP 握手队列占满时的 DoH 单点超时与解析挂起。
2. **系统直连 DNS 健壮性加固**：
   - `direct-nameserver` 配置为：`["223.5.5.5", "119.29.29.29", "system"]`，彻底解除对 Windows WinSock 单点解析的死绑。
3. **主配置入口显式禁用 IPv6**：
   - 在 JS 覆写主函数入口显式注入 `config.ipv6 = false;`，并在 YAML 覆写产物顶层注入 `ipv6: false`，彻底杀死底层 `connectex 10051` 幽灵重试。

### 2.8 地区策略组属地纯净性解耦与零节点动态物理剔除

#### 【问题根因：33ms 假延迟劫持陷阱】
- 过去为防止小地区无节点失效，向 6 核心地区 `url-test` 策略组注入了全局「自动选择」保底项。
- 这引发了严重的**跨区延迟劫持**：例如「美国节点」在测速时，因内嵌了「自动选择」，而「自动选择」通常选中了延迟仅 33ms 的香港或印尼节点；内核因此判定「美国节点」的最优链路为 33ms，导致美区流量被严重跨区漂移，破坏了分流规则的属地隔离原则。
- 此外，当某订阅完全没有某地区节点（如缺失韩国节点）时，仍生成该地区空策略组，不仅在 UI 上造成严重视觉噪音，还会引发内核无意义的空组并发测速与警告。

#### 【已落地优化方案】
1. **彻底剥离地区组中的全局动态组注入 (属地绝对纯净)**：
   - 从核心数据模型层及生成逻辑中彻底切除向 6 核心地区 `url-test` 组追加 `autoGroupName` / `自动选择` 的逻辑；
   - 地区策略组保持 100% 属地纯净，其测速延迟真实反映美国物理链路 (~180ms) 或香港物理链路 (~30ms)，绝不跨区漂移。
2. **JS 运行时零节点物理剔除引擎**：
   - 在 JS 覆写运行时 `main(config)` 中，利用已清洗节点池 `cleanProxies` 对各地区 filter 正则进行真值检测；
   - 若匹配节点数为 0（如当前订阅确实无韩国节点），**物理不生成该地区策略组**；
   - 配合现有的级联死链清洗引擎（`group.proxies.filter(...)`），自动将已删除的零节点地区组从「节点选择」、「AI 服务」等所有上游组的引用列表中剔除；
   - 界面整洁干净，从数据结构层面彻底消灭了零节点引发的内核测速死锁与 UI 噪音。
3. **绝对纯净属地代理 (彻底排除 DIRECT 与全局动态组)**：
   - 地区策略组（6 核心地区 + 其他国家）100% 仅由属地真实代理节点构成，**绝不混入 `DIRECT`（直连）或 `自动选择`**；
   - 杜绝用户或分流规则在指定走海外地区（如美国、香港）时，因意外回退至直连导致海外流量打入大陆网络被阻断（心情爆炸）的严重体验缺陷。
